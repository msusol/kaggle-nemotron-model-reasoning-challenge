## Context

- **Adapter downloaded**: `output/adapter_huikang_v26/` (1.5 GB, CC0-1.0)
  - Source: `andreyyunoshev/huikang-nemotron-adapter-mirror` on Kaggle
  - Config patched: `base_model_name_or_path` set to `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16`
- **Key difference from our adapters**: `target_modules: "all-linear"` vs our regex.
  This means LoRA weights exist for every linear layer including all 128 MoE experts
  independently — 1.5 GB vs 110 MB. More expressive but the same r=32, alpha=32.
- **Why this is a better GRPO seed**: Already trained to ~0.85 across all 14 categories
  including the 8 test-only augmenter types. GRPO starting here has rich signal from
  step 1; our v0.4-r2 had no signal for augmenter categories and may stall early.
- **See also**: `docs/plans/v0.6-grpo-plan.md` for GRPO algorithm background, memory
  budgets, reward function, and community insights.

## Key config differences vs original v0.5 plan

| Parameter | Original v0.5 plan | This plan |
|---|---|---|
| Init adapter | `output/adapter_huikang_v4_*` | `output/adapter_huikang_v26` |
| `target_modules` in GRPOConfig | specific regex | **`"all-linear"`** (match init adapter) |
| Adapter size | ~110 MB | ~1.5 GB |
| Expected step-0 accuracy | ~60–70% (v0.4-r2) | ~85% (huikang 0.85 quality) |

`target_modules` must match the loaded adapter's parameter space — using a different
regex would freeze the existing v26 LoRA weights and create new parameters, producing
a mixed adapter with undefined behaviour. Keep `"all-linear"` throughout GRPO training.

## Memory impact

`all-linear` targeting adds LoRA parameters for every linear layer. At inference time
(GRPO generation), the extra adapter size has minimal impact — forward pass memory is
dominated by activations, not adapter weights. At training time (backward pass), the
extra LoRA gradients add ~1.4 GB vs our v0.4 adapter. Still well within GB10's 128 GB.
