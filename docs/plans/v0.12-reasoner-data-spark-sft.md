## Training Journey — The DGX Spark Story

This section documents the DGX Spark training arc (v0.9 → v0.12) so the rationale for
v0.12's warmstart and design decisions is self-contained.

### Background: why Spark, and why expert LoRA matters

NemotronH is a hybrid MoE model. Its MoE expert layers (`mixer.experts.{j}.up_proj`,
`down_proj`) hold the vast majority of parameters. Unsloth — used on Kaggle's RTX Pro
6000 notebooks — injects LoRA into these layers using a fused kernel format
(`experts.w1/w2/w3` keys) that is incompatible with the standard PEFT evaluator
Kaggle uses at inference time. This means every Kaggle notebook run trained expert LoRA
locally but submitted only the attention adapter (~140 keys, 27M params); the 856M expert
LoRA params were silently discarded. Scores on those runs plateaued at 0.53–0.57 with no
path to improvement.

The DGX Spark GB10 (130.7 GB HBM) is the only hardware in our setup that can run the
full model without Unsloth's fused kernels, enabling per-expert LoRA injection in the
PEFT-compatible key format (`mixer.experts.{j}.up_proj.lora_A.weight`) that Kaggle's
evaluator can load. All v0.9 Spark runs (run12, run13) and v0.12 train on GB10.

### v0.9 on Spark — run12 (first attempt, packaging bug)

run12 was the first DGX Spark run with per-expert MoE LoRA injection:
- 883M trainable params (2.72%), 330 steps, seq=2048
- Expert LoRA trained correctly on Spark during the run
- **Bug**: `package_submission.sh` did not merge `expert_lora_weights.pt` into the
  submission safetensors — the 856M expert params were absent at Kaggle inference
- Score: 0.55 (same ballpark as Kaggle notebook runs, confirming the bug)

### v0.9 on Spark — run13 (first valid end-to-end run)

run13 fixed the packaging bug and ran the full 1000 steps:
- 878M trainable params (2.71%), 11,776 per-expert PEFT keys
- `package_submission.sh` now merges `expert_lora_weights.pt` → 11,962 total keys in submission
- Kaggle's evaluator loads all expert weights for the first time

**Checkpoint scores (DGX Spark → Kaggle submit):**

| Step | Train Loss | Kaggle Score | Notes |
|---|---|---|---|
| 100 | 0.2211 | 0.45 | Expert LoRA undertrained — lora_B max ≈ 0.035, adding noise |
| 500 | 0.1864 | **0.58** ★ | Epoch 2 boundary — new overall best |
| 600 | 0.1702 | 0.55 | Mid-epoch checkpoint — worse than boundary despite lower loss |
| 700 | 0.1380 | 0.57 | Epoch 3 boundary — recovers vs step 600 |
| 800 | 0.1265 | pending | Best train-loss checkpoint (intra-step low: 0.1202 @step ~908) |
| 1000 | — | — | Final checkpoint; to be submitted |

**Key pattern — epoch-boundary generalization:** checkpoints at epoch boundaries
(step 500, 700) score better on Kaggle than mid-epoch checkpoints (step 600) despite
having higher training loss. The data-loader reshuffle at each boundary acts as a
natural regularizer. Checkpoint loss also oscillates ±0.02–0.03 above intra-step
minimums — a batch-timing artifact, not stagnation.

**Mild overfitting after step 500:** training loss kept falling (intra-step low 0.1202
at ~step 908) while Kaggle scores oscillated 0.55–0.57 below the step-500 peak. The
model fits the training distribution increasingly well but generalizes less past the
epoch-2 boundary. This is expected for 1000 steps on 13,730 examples — not a failure,
just the natural limit of this dataset.

### v0.12 — why run13 step-1000 is the warmstart

run13 step-1000 is the only viable warmstart for v0.12:

- **856M expert LoRA params are now trained** — 25h of Spark time brought them from
  random init to a state that produces 0.58 on Kaggle. v0.12 warmstarting here inherits
  the full reasoning capability. Starting fresh would discard all of that.
- **Overfitting to one distribution is cured by a new distribution.** v0.12 uses
  25,500 rows (13,730 v0.9 + 11,770 augmented examples for under-represented categories).
  Training on a richer distribution from a warm initialization escapes the run13 overfit
  while preserving the learned reasoning format.
- **LR=1e-4** resets the optimization trajectory — the expert weights are a warm
  initialization, not a frozen endpoint. The model can adapt, not just fine-tune noise.

The analogy: a student who slightly over-studied one textbook still knows math far better
than someone who hasn't studied at all. A second textbook (v0.12 data) improves
generalization — it doesn't erase what they learned from the first.

## Motivation

GRPO on Spark (v0.11) is blocked on a startup OOM during HF→Megatron conversion.
5 days remain before the competition closes — not enough time to resolve v0.11 reliably.

The huikang corpus (which powers the 0.85 leaderboard leader) comes from deterministic
algorithmic solvers in `nemotron-master/reasoners/` and `nemotron-master/augmenters/`.
These are publicly available in `huikang/huikang-nemotron-repository-snapshot` on Kaggle.

The augmenters can generate **unlimited new problems** for all 16 categories, each
with a correct CoT trace — no LLM, no GRPO, no vLLM required. Spark's HBM has no
Kaggle quota limit, allowing longer training than the ~4.5h RTX Pro 6000 window.

## Architecture

```
huikang/huikang-nemotron-repository-snapshot
  └── augmenters/matching.py, splitting.py, concatenation.py, ...  ← generate new problems
  └── reasoners/bit_manipulation.py, cipher.py, gravity.py, ...    ← solve + narrate CoT

scripts/generate_reasoner_data.py
  → data/v0.12_augmented.jsonl  (new problems + traces, Format 4)

mix with data/v0.9_train.jsonl
  → data/v0.12_train.jsonl  (25,500 rows)

bash scripts/run_train_v9.sh          ← runs inside Docker via nemotron-gb10:latest
  WARMSTART_ADAPTER=output/adapter_v9_run13_ckpt   ← local path; = /workspace/output/... inside container
  → output/adapter_v12_spark/         ← local path; = /workspace/output/... inside container

bash scripts/package_submission.sh    ← runs on HOST (not inside Docker)
  output/adapter_v12_spark            ← local path, directly accessible
  → /tmp/submission_v12/submission.zip
```

**Workspace mount**: the project directory is bind-mounted as `/workspace` inside the
`nemotron-gb10` Docker container (`-v <project_dir>:/workspace`). All `output/`, `data/`,
and `scripts/` paths used in training commands are relative to the project root and resolve
to `/workspace/<path>` inside the container. Checkpoints written by the container land
directly in the local `output/` directory — no SSH, copy, or download step is needed.

## Key Design Decisions

**Augmenter-only, not reasoner-only**: The reasoners solve *existing* competition
problems (already in the huikang corpus). The augmenters generate *new* problems with
known answers. For v0.12 we use augmenters to add fresh examples, especially for the
8 test-only categories that currently have 571–1,500 examples each in v0.9 data.

**Target: 3,000 new examples per under-represented category** to balance the distribution:

| Category | v0.9 count | Target additional |
|---|---|---|
| `equation_numeric_deduce` | 573 | +2,427 → 3,000 |
| `spelling` | 571 | +2,429 → 3,000 |
| `lstrip` | 240 | +2,760 → 3,000 |
| `cryptarithm_deduce` | 97 | +2,903 → 3,000 |
| `equation_numeric` | 168 | +2,832 → 3,000 |
| `equation_symbolic` | 1 | skip (no augmenter) |
| Already well-covered (≥1,000) | — | no additional |

**Warmstart**: run13 step-1000 at `output/adapter_v9_run13_ckpt` (local project directory,
mounted as `/workspace/output/adapter_v9_run13_ckpt` inside Docker). This is the only
run with 11,776 per-expert PEFT keys trained end-to-end. No download required.

**Sequence length**: `MAX_SEQ_LENGTH=8192` on Spark (no 9-hour quota limit).
Huikang traces are typically 2,000–7,000 tokens; the full seq range is trainable on Spark.

| Risk | Mitigation |

| Generated data too similar to existing corpus | Accept — deduplication already applied; distribution shift from augmented categories is the main benefit |
| Warmstart loss starts higher than expected | Check that `expert_lora_weights.pt` loaded (look for `[moe-lora] Warmstart: loaded` in log) |
