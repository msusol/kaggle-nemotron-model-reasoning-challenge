# v0.4 Training OOM Investigation

Investigation into the `huikang_v4` training run (2026-05-31) that failed with exit 137
(kernel OOM kill) at 80% model weight loading, and the fix that resolved it.

---

## 1. CUDA allocator cache accumulation causes OOM at 80% weight loading

### Context

The v0.4 training run (`RUN_NAME=huikang_v4 bash scripts/run_train.sh`) loads
`nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16` (~57 GB in BF16) into a GB10 system
with 130.7 GB of unified LPDDR5X memory. The `_make_cache_dropper` background thread
drops Linux page cache every 20 seconds to prevent safetensors mmap pages from
crowding out CUDA allocations (established in ADR-0001/0002). The dropper was working:
by 80% loading, Linux cached pages were effectively zero. Despite this, the process
was killed by the kernel OOM killer at 80% (320/401 shards, ~5:37 elapsed).

Key observations from this log:

- `reserv` was locked at **63.2 GB from 0% to ~55%** — PyTorch pre-reserved a pool
  sized to the full model on container startup. No `cudaMalloc` expansion needed until
  the pool filled.
- From 55% onward, `reserv` expanded aggressively: 64.5 → 72.1 → 75.4 → 80.0 → 86.0
  → **90.3 GB** at the OOM point. Each expansion consumed real physical memory.
- At OOM: `reserv − alloc = 90.3 − 49.3 = **41.0 GB**` of freed-but-cached CUDA blocks
  sitting in the allocator pool, invisible to the CUDA driver.
- Linux `cached` was **0.1 GB** at the OOM point — the dropper had already done its job
  on page cache. The remaining 2.0 GB free was not recoverable by `drop_caches`.

#### Why the allocator accumulates freed blocks

`from_pretrained` with `low_cpu_mem_usage=True` loads each shard into CPU mmap then
copies to GPU. During the GPU copy, temporary tensors are created for dtype conversion,
contiguity checks, and safetensors buffer alignment. These are freed immediately, but
PyTorch's CUDA allocator retains the freed blocks in a per-stream free list rather than
calling `cudaFree`. This is correct behaviour for training (avoids repeated `cudaMalloc`
overhead during the forward pass), but across 401 shards it accumulates ~41 GB of
blocks the OS cannot reclaim.

When the initial 63.2 GB pool fills at ~55%, the allocator cannot pack new weight
tensors into the fragmented freed blocks and instead calls `cudaMalloc` to expand —
each expansion taking real physical memory from the already-thin free pool.

**Page cache was not the cause at the OOM point.** Linux cached = 0.1 GB and
active_file = 0.0 GB — the dropper had eliminated all mmap residue. The single
remaining culprit was the PyTorch allocator cache, which `drop_caches` cannot touch.

### Actions Taken

Added `torch.cuda.empty_cache()` to the dropper's `_loop()` in `scripts/train_lora.py`,
called immediately after `drop_caches` and before the memory stats print:

```python
def _loop():
    while not stop.wait(interval):
        try:
            with open("/proc/sys/vm/drop_caches", "w") as fh:
                fh.write("3\n")
        except OSError:
            pass  # non-privileged container — skip silently
        # Return freed CUDA blocks to the driver. During from_pretrained,
        # temporary dtype-conversion tensors accumulate as reserved-but-freed
        # allocator cache (~41 GB at 80% load) and crowd out the remaining
        # weight shards. empty_cache() releases them back to the OS pool.
        try:
            torch.cuda.empty_cache()
        except Exception:
            pass
        print(f"[dropper] {_mem_stats()}", flush=True)
```

`torch.cuda.empty_cache()` is thread-safe and only releases blocks in the
freed-but-retained list — it does not affect any active tensor allocations.

See ADR-0003 for the full rationale and alternatives considered.

### Resolution

**Status:** Resolved

The 2026-05-31 OOM was caused by the PyTorch CUDA allocator accumulating ~41 GB of
freed-but-cached blocks during `from_pretrained`, exhausting the physical memory pool
before the final 20% of weights could load. Adding `torch.cuda.empty_cache()` to the
dropper thread releases these blocks back to the driver every 20 seconds.

Verified: the retry run completed 401/401 shards in 6:42 with a maximum `gap` of
1.4 GB (vs 41.0 GB at the OOM point). Training started at step 1/948.
