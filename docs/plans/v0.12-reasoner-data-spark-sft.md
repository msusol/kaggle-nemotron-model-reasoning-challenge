## Training Journey — How We Got Here

This section documents the arc from v0.9 through run13 so the rationale for v0.12 is clear.

### The expert LoRA problem (runs 1–12)

NemotronH is a hybrid MoE model. Its MoE expert layers (`mixer.experts.{j}.up_proj`,
`down_proj`) account for the vast majority of parameters. Unsloth injects LoRA into
these layers using a fused kernel format (`experts.w1/w2/w3` keys) that is incompatible
with the standard PEFT evaluator Kaggle uses.

Every Kaggle run (run1–run7) trained the expert LoRA successfully locally, but submitted
only the attention adapter (140–232 keys, 27M trainable params). The 856M expert LoRA
parameters were silently discarded at submission time. Scores plateaued at 0.54–0.57.

run12 (DGX Spark, GB10) was the first attempt with per-expert injection
(`mixer.experts.{j}.up_proj.lora_A.weight` keys) that survive PEFT loading.
It trained successfully (883M params, 330 steps) but `expert_lora_weights.pt` was never
converted into PEFT-compatible safetensors, so the 856M expert params were again absent
at Kaggle inference. Score: 0.55.

### run13 — first valid end-to-end run

run13 (DGX Spark, GB10, 1000 steps, seq=2048) was the first run where:
- Expert LoRA was injected in the correct per-expert PEFT key format (11,776 keys)
- `package_submission.sh` merged `expert_lora_weights.pt` into safetensors before upload
- Kaggle's evaluator loaded all 11,962 keys (186 base + 11,776 expert)

**Checkpoint scores:**

| Step | Train Loss | Kaggle Score | Notes |
|---|---|---|---|
| 100 | 0.2211 | 0.45 | Expert LoRA too undertrained — lora_B max ≈ 0.035, adding noise |
| 500 | 0.1864 | **0.58** ★ | Epoch 2 boundary — new overall best |
| 600 | 0.1702 | 0.55 | Mid-epoch oscillation — worse than epoch boundary despite lower loss |
| 700 | 0.1380 | 0.57 | Epoch 3 boundary — recovers vs step 600 |
| 800 | 0.1265 | pending | Best train-loss checkpoint |
| 950 | 0.1340 | — | Epoch 4 approaching; oscillation continues |
| 1000 | — | — | Final checkpoint; to be submitted |

### The overfitting pattern

Training loss kept hitting new minimums (intra-step low: 0.1202 at ~step 908) but Kaggle
scores peaked at step 500 and oscillated 0.55–0.57 afterward. This is mild overfitting:
the model increasingly fits the specific training examples rather than generalizing.

Two structural observations:
1. **Epoch-boundary checkpoints generalize better** — steps 500 and 700 (epoch boundaries)
   score higher than step 600 (mid-epoch), despite step 600 having lower train loss. The
   data-loader reshuffle at each boundary acts as a natural regularizer.
2. **Checkpoint vs intra-step loss** — checkpoint loss oscillates ±0.02–0.03 above
   intra-step minimums. This is a batch-timing artifact, not a real plateau.

### Why run13 is still the right warmstart for v0.12

Even with mild overfitting, run13 step-1000 is categorically better than any alternative:

- **856M expert LoRA params** went from random init to fully trained over 25h. Starting
  v0.12 fresh would waste that entirely. Warmstarting inherits the reasoning format that
  produced the 0.58 score.
- **Overfitting to one distribution is cured by a new distribution.** v0.12 uses a
  25,500-row dataset with 11,770 augmented examples covering under-represented categories.
  Training on a fresh distribution from a good initialization escapes the local overfit
  while preserving the learned reasoning capability.
- **run4/run7 (0.53–0.56)** trained only 27M attention params (no expert LoRA). Using
  them as warmstart would mean expert LoRA re-initializes from random — the same mistake
  runs 1–12 made.
- **LR=1e-4** for v0.12 resets the optimization trajectory. The expert weights are used
  as warm initialization, not as a frozen endpoint.

The analogy: a student who over-studied one textbook still knows math better than someone
who hasn't studied at all. Teaching them from a different textbook (v0.12 data) improves
generalization — it doesn't erase what they learned.

## Motivation

GRPO on Spark (v0.11) is blocked on a startup OOM during HF→Megatron conversion.
5 days remain before the competition closes — not enough time to resolve v0.11 reliably.

The huikang corpus (which powers the 0.85 leaderboard leader) comes from deterministic
algorithmic solvers in `nemotron-master/reasoners/` and `nemotron-master/augmenters/`.
These are publicly available in `huikang/huikang-nemotron-repository-snapshot` on Kaggle.

The augmenters can generate **unlimited new problems** for all 16 categories, each
with a correct CoT trace — no LLM, no GRPO, no vLLM required. Spark's HBM has no
Kaggle quota limit, allowing longer training than the ~4.5h RTX Pro 6000 window.

## Key Design Decisions

**Augmenter-only, not reasoner-only**: The reasoners solve *existing* competition
problems (already in the huikang corpus). The augmenters generate *new* problems with
known answers. For v0.12 we use augmenters to add fresh examples, especially for the
8 test-only categories that currently have 571–1,500 examples each in v0.9 data.

**Target: 3,000 new examples per under-represented category** to balance the distribution:

| Category | v0.9 count | Target additional |
|---|---|---|
| `equation_numeric_deduce` | 573 | +2,427 → 3,000 |
| `spelling` | 571 | +2,429 → 3,000 |
| `lstrip` | 240 | +2,760 → 3,000 |
| `cryptarithm_deduce` | 97 | +2,903 → 3,000 |
| `equation_numeric` | 168 | +2,832 → 3,000 |
| `equation_symbolic` | 1 | skip (no augmenter) |
| Already well-covered (≥1,000) | — | no additional |

**Warmstart**: run13 step-1000 (`output/adapter_v9_run13_ckpt` on Spark).
This is the only run with 11,776 per-expert PEFT keys trained end-to-end.
run4/run7 (27M attn-only, no expert LoRA) are not viable warmstarts for v0.12.

**Sequence length**: `MAX_SEQ_LENGTH=8192` on Spark (no 9-hour quota limit).
Huikang traces are typically 2,000–7,000 tokens; the full seq range is trainable on Spark.

## Open Questions

1. **Augmenter API** — the exact interface of `augmenters/*.py` needs to be verified.
   Some augmenters may require seed problems from the competition dataset rather than
   generating fully from scratch.

2. **train_v9_sft.py `--save-steps`** — check if this flag exists; if not, add it so
   training is recoverable if Spark loses power or OOMs mid-run.

3. **Category imbalance strategy** — augmenting to 3,000/cat may still leave
   `equation_symbolic` (1 example) and `equation_numeric_guess` (160) under-represented.
   If the augmenter exists for these, include them.

4. **Learning rate** — running warmstarted from a 0.53–0.56 adapter at `lr=2e-4` may
   overwrite gains. Start at `lr=1e-4` and watch loss trajectory.

## Risks

| Risk | Mitigation |
|---|---|
| Augmenter requires seed problems (not standalone) | Use competition `data/train.csv` as seeds; augmenters may just vary parameters |
| `train_v9_sft.py` OOMs on Spark at seq=8192 | Fall back to seq=4096 (same as Kaggle runs) |
| Generated data is too similar to existing corpus | Add `--seed` variation to augmenters; or accept — more diverse examples still help |
| run7 doesn't complete before Spark run | Warmstart from run4 (0.56) instead |
