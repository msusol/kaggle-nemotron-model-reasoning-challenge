# v0.10 Training Plan — GRPO + vLLM Sidecar

> **Status: abandoned — superseded by v0.12 SFT.**
> This plan was written before v0.9 Spark runs (run12, run13) validated the expert LoRA
> path. Once run13 hit 0.58, the competition timeline favoured another SFT pass (v0.12)
> over a risky two-container GRPO setup. v0.11 (NeMo RL Megatron backend) was also
> skipped for the same reason. Neither v0.10 nor v0.11 were executed on the DGX Spark.

## Goal

Run GRPO self-improvement training (init from v0.5 adapter, 0.60 Kaggle) using a
vLLM FP8 sidecar for fast rollout generation, allowing more GRPO steps within the
competition deadline.

## Context

**Hardware history:** All SFT ran on Kaggle notebooks (RTX Pro 6000). All GRPO work
was planned for DGX Spark GB10, but hit OOM or key-format bugs before producing a
valid submission. DGX Spark SFT began with v0.9 run12 once the per-expert LoRA
PEFT format was understood.

| Version | Hardware | Method | Outcome |
|---|---|---|---|
| v0.1–v0.5 | Kaggle notebook | SFT | 0.49–0.60 |
| v0.6-grpo | DGX Spark GB10 | GRPO (Unsloth) | 330 steps, stopped — fused-key bug, declining rewards |
| v0.9 run12–run13 | DGX Spark GB10 | SFT, per-expert LoRA | 0.58 ★ (first valid) |
| v0.12 run14 | DGX Spark GB10 | SFT warmstart from run13 | active |
| **v0.10-grpo** | *(never run)* | GRPO + vLLM sidecar | **abandoned — OOM** |

**Why v0.10 and not v0.6/v0.7:** The GRPO sidecar is a fundamentally different
architecture — two containers, a custom standalone GRPO training loop (no TRL
GRPOTrainer), and FP8 quantized generation. It warrants its own major version.

**Why abandoned:** BF16 model peaks ~126 GB during load, leaving no headroom for a
vLLM sidecar on the 130.7 GB GB10. v0.11 was drafted to replace vLLM with NeMo RL
Megatron, but both plans were skipped when v0.9 run13 (0.58) made v0.12 SFT the
faster path to score improvement before the competition deadline.

## Architecture

Two Docker containers on GB10 (`--network=host`, both reach each other at localhost):

```
nemotron-vllm-gb10  nvidia/...-FP8  ~37 GB   rollout generation only
nemotron-gb10       nvidia/...-BF16  ~83 GB   GRPO loss + weight updates
────────────────────────────────────────────
                                    ~120 GB  fits 130.7 GB GB10 budget
```

The trainer sends prompts to `http://localhost:8000/v1/completions`, gets N=4
completions, computes group-relative advantages, runs forward+backward on the BF16
training model, and syncs the updated LoRA adapter to vLLM every 50 steps.

See `docs/adr/` for the GB10 memory management decisions (ADR-0001 through ADR-0004)
that apply equally here.

## Key Differences from v0.6 GRPO Plan

| | v0.6 plan | v0.10 (this) |
|---|---|---|
| TRL GRPOTrainer | Yes (`use_vllm=False`) | No — standalone loop |
| Generation | In-process `model.generate()` | External vLLM FP8 sidecar |
| KV cache in trainer | Yes (occupies ~16 GB) | No (in vLLM only) |
| Memory headroom | ~47 GB | ~10 GB (FP8) or ~22 GB (NVFP4) |
| Speed | ~38 tok/sec | ~150+ tok/sec (vLLM batching) |

## GRPO Loss

```
Advantage:   A_{b,g} = (R_{b,g} − mean_G(R)) / (std_G(R) + eps)
Policy loss: L_pg = −mean( A · Σ_t (log_π − log_π_ref) )
KL penalty:  L_kl = mean( Σ_t (log_π − log_π_ref) )   [clipped ≥ 0]
Loss:        L = L_pg + β · L_kl,   β = 0.04 (DeepSeek-R1 default)
π_ref = base model (LoRA disabled via model.disable_adapter())
```

## LoRA Sync Protocol

Every `ROLLOUT_SYNC_STEPS=50` steps:
1. `model.save_pretrained(rollout_path)` — saves current LoRA
2. Re-cast all tensors to BF16 on disk (FP8 base + BF16 adapter dtype safety)
3. `POST /v1/load_lora_adapter {"lora_name":"nemotron-policy","lora_path":...}`
4. vLLM hot-swaps the LoRA weights; subsequent completions use updated policy

This pattern is validated by the mineral-hr-llm project (github.com/msusol/mineral-hr-llm)
which ran vLLM + LoRA training as two separate containers on the same GB10 host.

## Scripts

| Script | Purpose |
|---|---|
| `scripts/run_grpo_sidecar.sh` | Orchestrates both containers: **start trainer first**, wait for `.trainer_model_ready`, then start vLLM sidecar + LoRA load |
| `scripts/train_grpo_sidecar.py` | Standalone GRPO loop; writes `.trainer_model_ready` after model load; waits for `.vllm_sidecar_ready`; generates via vLLM; syncs LoRA every N steps |
| `Dockerfile.vllm-gb10` | Updated: adds `peft`, optional NVFP4 flashinfer deps |
| `configs/nemotron_grpo.yaml` | Updated: adds sidecar config block |

## Startup Sequence (CRITICAL — unified memory pool)

```
run_grpo_sidecar.sh
  │
  ├─ 1. Drop page cache (pass 1)
  ├─ 2. docker run -d nemotron-gb10  ← training container starts loading BF16 (~126 GB peak)
  │
  ├─ 3. Poll .trainer_model_ready (written by train_grpo_sidecar.py after model load)
  │     ← BF16 steady state: ~83 GB committed, ~47 GB free
  │
  ├─ 4. Drop page cache (pass 2)
  ├─ 5. docker run -d nemotron-vllm-gb10  ← vLLM FP8 starts loading
  │     └─ 3s Alpine dropper runs concurrently to keep page cache low
  │        FP8 peak: 83 + ~10 (cache, aggressively dropped) + 32 (CUDA) ≈ 125 GB
  │
  ├─ 6. Poll vLLM /health until 200
  ├─ 7. POST /v1/load_lora_adapter (initial SFT adapter)
  ├─ 8. Write .vllm_sidecar_ready
  │
  └─ 9. train_grpo_sidecar.py detects .vllm_sidecar_ready → starts GRPO loop
        Steady state: ~83 GB (trainer) + ~37 GB (vLLM) = ~120 GB
```

## Open Questions

1. **`model.disable_adapter()` on Unsloth PeftModel** — verify the context manager works
   on the FastLanguageModel-wrapped PEFT model. If not, the fallback in
   `_maybe_disable_adapter()` uses `base_model.disable_adapter_layers()`.
2. **vLLM LoRA hot-swap API** — confirm `POST /v1/load_lora_adapter` is supported in the
   vLLM 0.8.x wheel in `nemotron-vllm-gb10`. If the endpoint doesn't exist, fallback:
   docker restart the vLLM container after each sync (adds ~3 min per sync).
3. **FP8 model + LoRA dtype** — if vLLM rejects BF16 LoRA on FP8 base, pass
   `--lora-dtype bfloat16` to the vLLM server command in `run_grpo_sidecar.sh`.
4. **Generation speed vs memory tradeoff** — if FP8 sidecar OOMs, switch to NVFP4
   by setting `SIDECAR_MODEL=NVFP4`.
