# v0.5 Regression: Unsloth vs Standard PEFT Adapter Key Mismatch

**Date:** 2026-06-03  
**Symptom:** v0.5-sft scored 0.56 despite clean training (train_loss=0.54, token_acc=87.2%)  
**Root cause:** Standard PEFT silently dropped 232 of v27's 418 adapter keys on load  
**Fix:** Merge dropped v27 keys back into saved adapter after training  

---

## 1. Background — Nemotron-H architecture

Nemotron-3-Nano-30B-A3B is a **hybrid Mamba-2 / attention MoE** model. Its 52 transformer
blocks fall into two categories:

### Attention blocks
Standard transformer blocks with multi-head attention:
- `q_proj`, `k_proj`, `v_proj` — query/key/value projections (nn.Linear)
- `o_proj` — output projection (nn.Linear)

These are standard `nn.Linear` layers fully accessible to both standard PEFT and Unsloth.

### Mamba-2 blocks
State-space sequence mixer blocks replacing attention in hybrid layers:
- `in_proj` — input projection (nn.Linear in some implementations)
- `out_proj` — output projection (nn.Linear)
- `gate_proj` — gating projection (**NOT a standard nn.Linear in Unsloth's patched model**)
- `x_proj` — SSM parameter projection (**NOT a standard nn.Linear in Unsloth's patched model**)
- `conv1d` — 1-D causal convolution (NOT a linear layer; excluded from LoRA)

### MoE blocks (Mixture of Experts FFN)
The FFN in MoE blocks uses **128 expert networks** plus shared experts. In the standard
`transformers` implementation, expert weights are stored as **batched 3-D tensors**
(not individual `nn.Linear` modules):

```
model.layers[i].mixer.experts   # shape: [128, d_ffn, d_model] — NOT nn.Linear
```

Unsloth patches the model to expose these as addressable LoRA targets using custom
key names:
- `mixer.experts.w1` — expert gate projections (batched)
- `mixer.experts.w2` — expert down projections (batched)
- `mixer.experts.w3` — expert up projections (batched)
- `mixer.shared_experts.up_proj` — shared expert up projection
- `mixer.shared_experts.down_proj` — shared expert down projection

In the standard `transformers` implementation, `mixer.experts` has no submodules with
these names because the weights are a raw `torch.Parameter` (3-D tensor), not a
collection of `nn.Linear` instances.

## 2. What PEFT's `all-linear` targets

`all-linear` in standard PEFT calls `get_linear_module_names()`, which walks the model's
`named_modules()` iterator and collects every module that is an instance of `nn.Linear`
(or `Linear4bit`, `Linear8bitLt` for quantized variants).

**Standard PEFT finds:**
- All attention `q/k/v/o_proj` ✅
- `in_proj`, `out_proj` (where they exist as nn.Linear) ✅
- Shared expert `up_proj`, `down_proj` (if exposed as nn.Linear) ✅ or ❌ depending on implementation

**Standard PEFT cannot find:**
- `mixer.experts.w1/w2/w3` — these are raw `torch.Parameter`, not `nn.Module` ❌
- `mixer.gate_proj`, `mixer.x_proj` — Unsloth renames/exposes these; not present in standard model ❌

**Unsloth patches the model before calling `get_peft_model`**, replacing batched 3-D
expert parameters with custom `Linear` wrappers that expose them as `nn.Linear`-like
objects. This lets Unsloth's `all-linear` target layers that standard PEFT physically
cannot see.

## 3. The key naming difference

When PEFT saves an adapter, the key format is:

```
base_model.model.<module_path>.lora_A.default.weight
base_model.model.<module_path>.lora_B.default.weight
```

**Standard PEFT keys (v5, 232 tensors):**
```
base_model.model.model.layers.0.mixer.in_proj.lora_A.default.weight
base_model.model.model.layers.0.mixer.in_proj.lora_B.default.weight
base_model.model.model.layers.0.mixer.o_proj.lora_A.default.weight
...
base_model.model.model.layers.0.mixer.q_proj.lora_A.default.weight
...
```

**Unsloth-only keys (in v27 but not loadable by standard PEFT, 232 tensors):**
```
base_model.model.model.layers.0.mixer.gate_proj.lora_A.weight        ← no ".default."
base_model.model.model.layers.0.mixer.gate_proj.lora_B.weight
base_model.model.model.layers.0.mixer.x_proj.lora_A.weight
base_model.model.model.layers.0.mixer.x_proj.lora_B.weight
base_model.model.model.layers.1.mixer.experts.w1.lora_A.weight       ← MoE expert
base_model.model.model.layers.1.mixer.experts.w1.lora_B.weight
base_model.model.model.layers.1.mixer.experts.w2.lora_A.weight
base_model.model.model.layers.1.mixer.experts.w2.lora_B.weight
base_model.model.model.layers.1.mixer.experts.w3.lora_A.weight
base_model.model.model.layers.1.mixer.experts.w3.lora_B.weight
base_model.model.model.layers.1.mixer.shared_experts.down_proj.lora_A.weight
base_model.model.model.layers.1.mixer.shared_experts.down_proj.lora_B.weight
base_model.model.model.layers.1.mixer.shared_experts.up_proj.lora_A.weight
base_model.model.model.layers.1.mixer.shared_experts.up_proj.lora_B.weight
...
```

Two notable differences in the Unsloth key format:
1. **No `.default.` adapter name segment** — Unsloth uses `lora_A.weight` directly;
   standard PEFT uses `lora_A.default.weight` (where `default` is the adapter name)
2. **Non-standard module paths** — `experts.w1/w2/w3` and `gate_proj/x_proj` don't
   correspond to modules accessible via `named_modules()` in standard transformers

## 4. What happens during `PeftModel.from_pretrained(v27, is_trainable=True)`

```
PeftModel.from_pretrained(base_model, v27_dir, is_trainable=True)
```

Step-by-step:

1. **Read `adapter_config.json`**: `target_modules = "all-linear"`, `r = 32`
2. **Call `get_peft_model`**: standard PEFT walks `named_modules()`, finds 90 `nn.Linear`
   layers, creates LoRA A/B matrices for each → produces 180 standard-path keys
3. **Load `adapter_model.safetensors`**: attempt to match each of v27's 418 keys to
   the model's named parameters
   - 186 keys match standard paths → loaded ✅
   - 232 Unsloth-only keys → no matching parameter found → silently ignored ⚠️
4. **Missing keys warning** (the `in_proj` warning we saw): these 52 keys exist in the
   model (standard PEFT created LoRA for `in_proj` because it IS an `nn.Linear` in
   the standard transformers model) but are absent from v27's checkpoint (Unsloth
   apparently did not include `in_proj` in its LoRA). PEFT initialises them fresh
   (lora_B = zero → identity at start).

**Net result after loading:**
- 90 LoRA modules loaded from v27 (standard attention/output layers)
- 26 LoRA modules initialised fresh (in_proj — not in v27)
- 232 Unsloth-only keys silently dropped (MoE experts, gate_proj, x_proj)

Total trainable parameters: **27,711,488** (only the 116 standard LoRA modules)

## 5. Why the score regressed to 0.56

v27's 1.5 GB adapter breaks down approximately as:

| Layer type | Keys | Size estimate | Contribution |
|---|---|---|---|
| Standard attention LoRA (q/k/v/o/in/out) | 186 | ~80 MB | ✅ loaded by PEFT |
| MoE expert LoRA (experts.w1/w2/w3) | ~150 | ~1.2 GB | ❌ dropped by PEFT |
| Mamba LoRA (gate_proj, x_proj) | ~52 | ~200 MB | ❌ dropped by PEFT |
| Shared expert LoRA (up/down_proj) | ~30 | ~100 MB | ❌ dropped by PEFT |

The MoE experts process **every token's FFN computation** and represent the bulk of the
model's 3B active parameters (out of 30B total). With 128 experts per MoE block and
a top-K routing mechanism, the MoE layers contribute the majority of the model's
task-specific knowledge.

By dropping the MoE expert LoRA entirely:
- The model's FFN layers run on **base model weights** (pre-fine-tuning)
- Only the attention layers carry v27's fine-tuning signal
- The result is a partial adapter that degrades the model's ability to apply v27's
  learned reasoning patterns

The 0.56 score (≈ v0.1 baseline) is consistent with attention-layer LoRA alone being
insufficient to override the base model's generic behaviour.

## 6. The fix: post-save key merge

After training completes and `model.save_pretrained()` writes the standard 232-key
adapter, we reopen the v27 safetensors file and merge all 418 keys:

```python
# Start with ALL of v27's keys (including Unsloth-only ones)
merged = {k: v27.get_tensor(k) for k in v27.keys()}

# Overwrite with our trained weights where we have them (186 shared keys)
# Add new keys we trained that v27 didn't have (46 keys, e.g. in_proj)
merged.update(trained_tensors)

save_file(merged, output_path)
```

**Result:**
- 464 total keys (418 v27 + 46 new from our training, minus 186 shared/overwritten)
- 1.58 GB (matches v27 scale)
- Contains v27's MoE expert knowledge + our 240-step short-response SFT updates

| Keys | Source | Content |
|---|---|---|
| 186 | Our training (overwrite v27) | Updated attention LoRA from 240-step SFT |
| 46 | Our training (new) | Fresh in_proj LoRA trained from scratch |
| 232 | v27 (preserved) | MoE expert + Mamba LoRA; never updated by our training |

## 7. Limitations of this approach

### MoE experts are frozen at v27 state
Our 240-step SFT only updates the 90 standard attention/output LoRA layers. The 232
Unsloth-only keys (MoE experts, gate_proj, x_proj) are copied unchanged from v27.
This means the model's FFN behaviour is entirely v27's — our SFT can only shift the
model through attention-layer updates.

For a true joint update (attention + MoE experts together), Unsloth would need to be
installed in the training container. Unsloth's custom model patches expose the MoE
expert tensors as trainable LoRA targets, enabling all 418 keys to be updated in a
single training pass.

### Key format incompatibility
The Unsloth-only keys use `lora_A.weight` (no `.default.` segment). Standard PEFT uses
`lora_A.default.weight`. When the merged adapter is loaded at Kaggle inference time,
the behaviour depends on which PEFT version and which model loader the prize notebook uses:

- **If using Unsloth**: all 464 keys load correctly ✅
- **If using standard PEFT**: the 232 Unsloth-only keys are silently dropped again (same
  problem as before) ❌

This means the merged adapter **only fully works if the Kaggle evaluator uses Unsloth
or a PEFT version that handles both key formats**. If the evaluator uses standard PEFT,
the non-standard keys cause a crash.

**Confirmed (2026-06-03):** `v0.5-sft-merged` returned `"Evaluation metric raised an
unexpected error"` — same error as `v0.4-huikang-v26` (which submitted v27 directly).
**Kaggle's evaluator uses standard PEFT, not Unsloth.**

The crash is not a silent skip — standard PEFT raises an error when it encounters keys
that don't match the expected `lora_A.default.weight` format or module paths it cannot
resolve to model parameters. The merged adapter is therefore **not submittable** to this
competition without stripping the Unsloth-format keys first (which reduces it back to
the 232-key standard adapter scoring 0.56).

### Alternative A: use Unsloth for training

If Unsloth is installed in the `nemotron-gb10` Docker image, `PeftModel.from_pretrained`
would use Unsloth's patched model and load all 418 keys. Training would update all layers.
The saved adapter would naturally contain all 418+ keys with no post-merge step needed.

Unsloth does two things, only one of which we need:

**Model patching (needed):** Pure Python — replaces the MoE experts' batched 3-D
`torch.Parameter` tensors with custom `nn.Linear`-like wrapper objects before
`get_peft_model` runs. This makes `mixer.experts.w1/w2/w3`, `gate_proj`, and `x_proj`
visible to PEFT's `named_modules()` walk. No CUDA compilation required.

**Optimized triton/CUDA kernels (not needed):** Custom fused kernels for attention and
cross-entropy. These require architecture-specific compilation and would need a full
source build for Blackwell SM_120 — the same friction we experienced with `mamba_ssm`
and `causal_conv1d`.

**Risk: version conflicts.** Unsloth pins specific versions of `transformers` and `peft`.
We pin `transformers==5.5.3` for the NemotronH KV cache fix. Unsloth may force a
downgrade, breaking inference. Installing with `--no-deps` and re-pinning transformers
afterward is possible but risky if Unsloth's patches depend on internal transformers APIs.

This needs a dedicated investigation before touching `Dockerfile.gb10`. See
`docs/plans/TODO.md` — this is a candidate for the v0.6 GRPO phase.

### Alternative B: use NeMo Framework for training

NeMo is NVIDIA's own training stack. Since NVIDIA built both NeMo and Nemotron, NeMo's
model definition exposes the MoE expert tensors and Mamba projections as proper trainable
objects. A NeMo LoRA training run would cover all layers including `experts.w1/w2/w3`
and `gate_proj`/`x_proj`.

**However, NeMo does not solve the Kaggle submission problem.**

NeMo saves checkpoints in `.nemo` format — a proprietary NVIDIA archive. Kaggle's
submission format requires HuggingFace PEFT (`adapter_config.json` +
`adapter_model.safetensors`). Converting NeMo LoRA → HuggingFace PEFT requires mapping
NeMo's internal key naming to PEFT's convention:

| Layer | NeMo key (approximate) | HuggingFace PEFT key |
|---|---|---|
| Attention Q | `model.decoder.layers.0.self_attention.linear_q.lora_A` | `base_model.model.model.layers.0.mixer.q_proj.lora_A.default.weight` |
| MoE expert | `model.decoder.layers.1.mlp.experts.local_experts.0.linear_fc1.lora_A` | `base_model.model.model.layers.1.mixer.experts.w1.lora_A.weight` |

This mapping is non-trivial, not officially documented, and would likely reproduce the
same silent key-drop problem in reverse — converted keys that don't match what the
Kaggle evaluator's PEFT loader expects.

**NeMo summary:** solves training coverage but creates a new conversion problem for
Kaggle submission. It is valuable for other reasons (distributed training, production
features) but is not the right tool for this specific submission format constraint.

### Solution hierarchy

| Approach | Trains MoE experts? | Kaggle-compatible output? | Effort |
|---|---|---|---|
| Standard PEFT (current) | ❌ | ✅ (incomplete) | — |
| Merge fix (current workaround) | ✅ frozen at v27 | ✅ if Kaggle uses Unsloth | Done |
| **Unsloth in Docker** | ✅ fully trained | ✅ native PEFT format | Medium — version risk |
| NeMo training | ✅ fully trained | ⚠️ requires conversion script | High — format mismatch |

## 8. Open question — how does kuangyicheng's 0.87 work?

Kaggle uses standard PEFT (confirmed). kuangyicheng trained with Unsloth on Modal.com
and submitted an adapter that scores 0.87. If Kaggle's evaluator crashes on Unsloth-format
keys, how does kuangyicheng's submission succeed?

**Hypothesis A: kuangyicheng's save step outputs standard PEFT format**

When Unsloth patches the model and training completes, calling `model.save_pretrained()`
uses PEFT's standard save function. For the standard-path layers (attention, output),
PEFT saves `lora_A.default.weight` format. For the Unsloth-only layers (MoE experts,
gate_proj), Unsloth may save them with the non-standard format OR may skip them entirely
if PEFT's save doesn't enumerate them.

If kuangyicheng's saved adapter contains only standard-path keys (despite training on
all layers), Kaggle would load it fine. The MoE expert updates would be incorporated
into the base model weights via a merge step, not carried as separate LoRA keys.

**Hypothesis B: kuangyicheng merges LoRA into base weights before submitting**

Some Unsloth workflows call `model.merge_and_unload()` before saving, which bakes the
LoRA updates directly into the base model weights. The resulting saved artifact is not
a PEFT adapter at all — it's a full fine-tuned model (or a weight diff). The competition
submission might accept something other than a raw LoRA adapter if the prize notebook
handles this case.

**Hypothesis C: kuangyicheng's 0.87 comes only from attention-layer LoRA**

If kuangyicheng's Unsloth training only effectively updated the standard attention layers
(and the MoE expert updates were lost on save), then the 0.87 score is achievable with
standard PEFT-format keys alone. In that case, our 0.56 is a data or training quality
problem, not a key coverage problem.

**Implication for our pipeline**

We cannot determine which hypothesis is correct without inspecting kuangyicheng's actual
submission zip. What we know:

- Standard PEFT adapter (232 keys): loads fine, scores 0.56
- Merged adapter (464 keys with Unsloth format): crashes evaluator
- v27 submitted directly: crashes evaluator

The path to ≥ 0.85 must therefore go through one of:
1. **Installing Unsloth in the training container** so that `save_pretrained` naturally
   outputs evaluator-compatible keys while having trained on all layers
2. **Improving training on the standard 232 keys** — more steps, better data, different
   hyperparameters — to see if attention-layer LoRA alone can reach 0.85+
3. **Understanding kuangyicheng's exact save format** by pulling their submission zip
   from Kaggle and inspecting its key count and format
