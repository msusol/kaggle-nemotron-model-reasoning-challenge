# v0.11 Standalone HF→Megatron Pre-Seed Conversion

**Date:** 2026-06-10
**Branch:** main
**Depends on:** `docs/investigate/v0.11-grpo-spark-smoke-tests.md`
**Goal:** Eliminate the `iter_0000000` save OOM by pre-seeding the Megatron
checkpoint in an isolated process, so the training run skips the conversion.

---

## TL;DR

Run the conversion **once, alone**, before training:

```bash
tmux new -s convert
bash scripts/run_convert_spark.sh          # writes a complete iter_0000000/
# then, unchanged:
SMOKE_TEST=1 RUN_NAME=grpo_v11_smoke bash scripts/run_nemo_grpo_spark.sh
```

The training worker detects the existing complete checkpoint and **skips the
HF→mcore import entirely**, so the 54 GB save never runs during training launch.

---

## Why the handoff's "skip init save" patch is the wrong fix

The original plan was to patch `megatron_policy_worker.py` to skip the
iteration-0 save when `iter_0000000` exists. The smoke-test investigation
already tried this (smoke11) and it **breaks the reload**:

`MegatronPolicyWorker.__init__` does, in order:

1. `pt_checkpoint_exists = exists(pretrained_path/iter_0000000)` — directory check only.
2. If not present → `import_model_from_hf_name(...)` → `bridge.save_megatron_model(...)`
   writes `iter_0000000/` (weight shards **+ `run_config.yaml`**).
3. Reads `iter_0000000/run_config.yaml`; if absent → `FileNotFoundError` → exit 255.
4. Builds the training model from that config and **loads weights from the
   saved checkpoint** (`load_checkpoint`) before training.

So the save is not optional scaffolding — the worker reloads from it. Skipping
the save (or leaving a partial `common.pt`) removes `run_config.yaml` and the
weight shards, and step 3/4 fail. This is exactly the FileNotFoundError seen in
smoke11/13/14.

## Why pre-seeding is the right fix (and not a hack)

`pt_checkpoint_exists == True` is the worker's **own** intended fast path: when
a complete checkpoint already exists it prints *"Checkpoint already exists …
Skipping import."* and goes straight to the cheap `load_checkpoint`. We just
produce that checkpoint ahead of time, in a process that isn't also holding the
Ray actor stack — giving the single 54 GB save the entire machine.

`scripts/convert_hf_to_megatron_spark.py` calls the **identical** function the
worker uses:

```python
from nemo_rl.models.megatron.community_import import import_model_from_hf_name
import_model_from_hf_name(hf_model_name, pretrained_path, megatron_cfg, **hf_overrides)
# -> AutoBridge.from_hf_pretrained(...).to_megatron_provider(load_weights=True)
# -> bridge.save_megatron_model(model, pretrained_path)   # writes iter_0000000/
```

Because it is the same call with the same `policy.megatron_cfg` from
`04-lora-grpo-config.yaml`, the produced checkpoint is format-identical to what
training expects.

## Path matching (must be exact)

The script resolves the output path the same way the worker does
(`get_megatron_checkpoint_dir()` + model subdir). With `HF_HOME=/workspace/.cache/huggingface`:

```
/workspace/.cache/huggingface/nemo_rl/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/iter_0000000/
```

This directory is on the mounted HF cache volume, so it persists after the
conversion container exits and is visible to the training container (same mount).

## Why isolation gives more headroom

| Resident during save | Worker path (smoke9–15) | Standalone (this) |
|----------------------|-------------------------|-------------------|
| mcore model (BF16)   | ~54 GB                  | ~54 GB            |
| CPU save copy        | ~54 GB                  | ~54 GB            |
| Freed HF page cache  | up to ~39 GB            | dropped every 10 s |
| Ray actor / object store | yes                 | none              |
| Optimizer / ref model / KV cache | built later, but actor overhead present | none |

Same fundamental save cost, but nothing competes with it, and `run_convert_spark.sh`
applies the proven mitigations from `run_nemo_grpo_spark.sh`: 60 GB extra swap,
`swappiness=100`, VM dirty-ratio tuning, and a host-side page-cache dropper.

## Interaction with the existing wrapper auto-clean

`run_grpo_wrapper.py` step 3b deletes `iter_0000000/` only if it is **< 100 MB**
(a crashed partial save). A complete pre-seed (~54 GB) is far above that
threshold, so it survives and the worker skips the import. No conflict.

## Runbook

1. **Build image** (if not already): `nemo-rl-spark:latest` from
   `docs/plans/lora-grpo-spark-plan/Dockerfile.spark`.
2. **Model cached**: ensure the HF weights are in
   `.cache/huggingface` (via `scripts/download_model_spark.sh`); conversion runs
   with `HF_HUB_OFFLINE=1`.
3. **Convert** (in tmux): `bash scripts/run_convert_spark.sh`
   - Watch for `import_model_from_hf_name (this is the heavy step)` then
     `DONE. iter_0000000 size=~54GB` and `run_config.yaml present`.
   - If it OOMs, raise swap: `SWAP_GB=90 bash scripts/run_convert_spark.sh`.
4. **Verify**:
   ```bash
   du -sh .cache/huggingface/nemo_rl/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/iter_0000000
   ls    .cache/huggingface/nemo_rl/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/iter_0000000/run_config.yaml
   ```
5. **Train** (unchanged): the launch now skips the import.
   ```bash
   SMOKE_TEST=1 RUN_NAME=grpo_v11_smoke bash scripts/run_nemo_grpo_spark.sh
   ```
   Expect the log line `Checkpoint already exists at … Skipping import.`

## Gotcha: must run under the venv interpreter

`megatron-bridge` is an **editable** install in `/opt/nemo-rl/.venv`. Its
`megatron.bridge` import is wired up by the venv's `site.py` at interpreter
startup, so running the script under the system `python3` (even with
`site-packages` appended to `sys.path`) fails with
`ModuleNotFoundError: No module named 'megatron.bridge'`. The launcher therefore
invokes `/opt/nemo-rl/.venv/bin/python3` — the same interpreter NeMo-RL uses for
the real MegatronPolicyWorker. `LD_PRELOAD=…/libnccl.so.2` (set in the launcher)
loads system NCCL first, so the `ncclAlltoAll` symbol crash does not occur under
the venv python. (First-run failure 2026-06-10 00:53 was exactly this; fixed.)

## Open items / risks to watch

- **Format drift:** if `nemo-rl-spark:latest` is rebuilt with a newer
  megatron-bridge after pre-seeding, the saved checkpoint may fail
  `ConfigContainer.from_yaml(... STRICT)`. Re-run with `FORCE=1` after any image
  rebuild.
- **`pipeline_dtype` as string:** the script passes `megatron_cfg` straight
  from YAML (string `"bfloat16"`), exactly as the worker passes its config —
  same code path, same behavior. If Hydra structured-typing in the training run
  converts it to a `torch.dtype` before the worker sees it, that conversion is
  irrelevant here because the save only records the resolved model config.
- **Not yet executed:** these scripts were authored from the nano-v3 source but
  have not been run on the Spark. First run is the real test (equivalent to the
  investigation's smoke15+ but isolated).
