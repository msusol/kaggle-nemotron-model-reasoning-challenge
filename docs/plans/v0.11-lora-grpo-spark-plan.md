# v0.11 Training Plan — LoRA GRPO on DGX Spark (NeMo RL + Megatron backend)

**Status**: planned  
**Hardware**: DGX Spark (Blackwell GB10, aarch64, 130.7 GB HBM + 121 GB LPDDR5x)  
**Target score**: >0.70 (GRPO RL phase on top of v0.9 SFT)

---

## Why v0.11 Instead of v0.10 on Spark

v0.10 was the planned DGX Spark GRPO approach: a BF16 training container (~83 GB HBM)
+ a vLLM FP8 sidecar (~37 GB HBM) totalling ~120 GB, leaving ~10 GB headroom.

**The two-container approach does not fit on DGX Spark.** During load, the BF16 trainer
peaks at ~126 GB — exhausting the 130.7 GB HBM budget before vLLM can start. There is
no room to bring up a second CUDA process alongside the training model.

Additionally, the standard NVIDIA container runtime flags (`--gpus all`, `--runtime=nvidia`)
fail on Spark with a bind-mount error (`open /usr/bin/nvidia-cuda-mps-control: no such file`),
and the `--network=host` two-container coordination pattern is unvalidated on the Spark
software stack.

v0.11 solves this by eliminating vLLM entirely and using **NeMo RL's Megatron inference
backend**, which reuses the frozen base weights already in HBM for rollout generation —
no second process, no weight copy, no refit buffer.

### Memory comparison

| Approach | HBM peak (load) | HBM steady state | Fits Spark? |
|---|---|---|---|
| v0.10 two-container (BF16 + FP8) | ~126 GB (trainer alone) | ~120 GB | ❌ no room for vLLM |
| v0.11 NeMo RL + Megatron backend | ~126 GB (load phase only) | ~85 GB | ✅ ~45 GB headroom |

### Memory budget at steady state (v0.11)

| Component | Estimate | Notes |
|---|---|---|
| Base weights (BF16, frozen) | ~60 GB | shared with Megatron generation |
| LoRA adapters (r=32) | ~0.5 GB | trainable parameters only |
| Adam optimizer (LoRA only) | ~1–2 GB | covers adapter params, not full model |
| Gradients (LoRA only) | ~0.5 GB | |
| Activations + activation ckpt | ~10–15 GB | with `activation_checkpointing=true` |
| KV cache (Megatron gen) | ~12 GB | `buffer_size_gb` in config |
| **Total estimated** | **~85 GB** | **~45 GB headroom** |

## Architecture

Single container, single GPU. NeMo RL on the `nano-v3` branch runs both training and
rollout generation inside the same Megatron process. The frozen BF16 base weights serve
as both the reference policy (π_ref) and the rollout model; only the small LoRA adapter
matrices are updated during training.

```
nemo-rl-spark:latest  (single container, --privileged)
│
├── Megatron training engine  ←→  LoRA adapter (r=32, ~0.5 GB)
│         │                          │
│         └── Frozen BF16 base (~60 GB HBM)
│                    │
│                    └── Megatron inference backend
│                         (reuses base weights for rollout generation)
│
└── NeMo Gym reward environments (math, science_qa, etc.)
```

No sidecar, no HTTP calls, no weight sync protocol. The Megatron backend replaces
the vLLM dependency entirely.

## Key Config Deltas from the Official 2-Node Recipe

The config at `docs/plans/lora-grpo-spark-plan/04-lora-grpo-config.yaml` is adapted
from the official `grpo-nanov3-30BA3B-2n8g-megatron-lora.yaml`. Every Spark-specific
override is annotated `# SPARK`:

| Parameter | Official value | Spark value | Reason |
|---|---|---|---|
| `cluster.num_nodes` | 2 | 1 | single machine |
| `cluster.gpus_per_node` | 8 | 1 | single GB10 GPU |
| `policy.max_total_sequence_length` | 8192 | 4096 | KV cache + activation budget |
| `megatron_cfg.tensor_model_parallel_size` | 4 | 1 | single GPU |
| `megatron_cfg.expert_model_parallel_size` | 8 | 1 | all MoE experts on 1 GPU |
| `generation.backend` | `vllm` | `megatron` | eliminates vLLM process entirely |
| `generation.mcore_generation_config.num_cuda_graphs` | 16 | 8 | reduce HBM overhead |
| `grpo.num_generations` | 8 | 4 | reduce KV cache pressure |
| `grpo.rollout_batch_size` | 512 | 32 | single-GPU scale-down |
| `grpo.global_batch_size` | 256 | 16 | single-GPU scale-down |

## Warmstart Strategy

v0.11 initialises from the best available SFT adapter in this priority order:

1. **`output/adapter_v9_sft`** — v0.9 SFT adapter (base model init, all 16 cats, format 4; preferred)
2. **`output/adapter_v5_sft_unsloth`** — v0.5 SFT-Unsloth (0.60 Kaggle; fallback if v0.9 not yet complete)

The NeMo RL Megatron backend requires Megatron-format adapter weights, not the
HuggingFace PEFT format. The export step below produces the HF merge; no Megatron
pre-conversion is needed for the warmstart (NeMo RL converts on load).

## Tasks

### Phase A — Build and validate environment

- [ ] Build `nemo-rl-spark:latest` on DGX Spark
  ```bash
  docker build \
    -f docs/plans/lora-grpo-spark-plan/Dockerfile.spark \
    --build-arg MAX_JOBS=8 \
    -t nemo-rl-spark:latest \
    .
  ```
  See `01-docker-build.md` for expected build time (~30–90 min) and `MAX_JOBS` rationale.
- [ ] Run HBM preflight cleanup: stop gnome-remote-desktop, drop page cache, verify ≥ 65 GB free
- [ ] Inside container: verify GPU (`torch.cuda.get_device_name(0)`), HBM, and all packages
  (`transformers ≥ 5.5.3`, `causal_conv1d`, `mamba-ssm`, `nemo_rl` on `nano-v3` branch)

### Phase B — Data and model

- [ ] Copy or symlink `data/v0.9_train.jsonl` + `data/v0.9_valid.jsonl` into the Spark workspace
- [ ] Confirm BF16 model cached or download to `/workspace/model/`:
  ```bash
  huggingface-cli download \
    nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 \
    --local-dir /workspace/model \
    --local-dir-use-symlinks False
  ```
- [ ] Apply tokenizer chat template patch (`enable_thinking=false`) per `02-environment-setup.md`

### Phase C — Validation run (3 steps)

- [ ] Launch 3-step validation in tmux:
  ```bash
  tmux new -s spark_validate
  cd /opt/nemo-rl
  TORCH_CUDA_ARCH_LIST="12.1" \
  HF_HOME=/workspace/.cache/huggingface \
  uv run python examples/nemo_gym/run_grpo_nemo_gym.py \
    --config /workspace/docs/plans/lora-grpo-spark-plan/04-lora-grpo-config.yaml \
    grpo.max_num_steps=3
  ```
- [ ] Confirm: rollout generation completes, `mean_reward > 0`, no OOM
- [ ] Confirm HBM usage ≤ 125 GB during the 3-step run

### Phase D — Full training run

- [ ] Remove `max_num_steps=3` override, run full training in tmux:
  ```bash
  tmux new -s spark_train
  cd /opt/nemo-rl
  EXP_NAME="$(date +%Y%m%d)/grpo-spark/full-run-001"
  mkdir -p /workspace/results/$EXP_NAME/logs
  TORCH_CUDA_ARCH_LIST="12.1" \
  HF_HOME=/workspace/.cache/huggingface \
  uv run python examples/nemo_gym/run_grpo_nemo_gym.py \
    --config /workspace/docs/plans/lora-grpo-spark-plan/04-lora-grpo-config.yaml \
    checkpointing.checkpoint_dir=/workspace/results/$EXP_NAME \
    logger.log_dir=/workspace/results/$EXP_NAME/logs \
    2>&1 | tee /workspace/results/$EXP_NAME/logs/output.log
  ```
  Target: 200–500 steps on math/science_qa NeMo Gym environments.

### Phase E — Export and submit

- [ ] Export LoRA checkpoint to HF format per `06-checkpoint-export.md`:
  ```bash
  uv run --extra mcore python examples/converters/convert_lora_to_hf.py \
    --base-ckpt  /workspace/results/$EXP_NAME/policy/weights/iter_0000000 \
    --adapter-ckpt /workspace/results/$EXP_NAME/policy/weights/iter_<STEP> \
    --hf-model-name nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 \
    --hf-ckpt-path /workspace/results/v0.11-merged-hf
  ```
- [ ] Verify exported model generates correct boxed answers on 10 validation examples
- [ ] Re-enable `enable_thinking=true` in exported tokenizer (for Kaggle inference)
- [ ] Package and submit to Kaggle; update `docs/plans/leaderboard.md`

## Monitoring Key Metrics

| Metric | Healthy | Warning |
|---|---|---|
| `mean_reward` | increasing | flat from step 1 |
| `reward_std` | > 0 | 0 → all completions identical |
| `kl_divergence` | < 0.5 | > 1.0 → reduce `kl_coeff` |
| HBM used | < 120 GB | > 125 GB → OOM risk |
| Tokens/sec (generation) | > 100 tok/s | < 50 → chunked prefill issue |

## Open Questions

1. **NeMo Gym environment for competition data** — the config currently points to the `math`
   environment. The competition problems (bit_manipulation, cipher, equation_numeric, etc.)
   need a custom NeMo Gym reward function or the `math` verifier adapted for `\boxed{}` extraction.
   Option: use the standalone verifier from `scripts/validate_metric.py` as the reward signal
   via a custom environment wrapper.

2. **Warmstart format** — NeMo RL Megatron backend expects its own checkpoint format.
   Loading a PEFT/HF adapter as the warmstart requires the HF→Megatron conversion step.
   Confirm `convert_hf_to_megatron.py` handles LoRA adapter weights or whether a full-weight
   merge is needed before conversion.

3. **ptxas sm_121a warnings** — the `nano-v3` Dockerfile applies the ptxas wrapper fix from
   `docs/adr/0005-ptxas-blackwell-fix.md` (if it exists) or the permanent symlink patch from
   v0.9 commit `b7c575d`. Confirm the patch is present in `Dockerfile.spark` before building.

4. **Sequence length vs throughput** — the config uses `max_total_sequence_length=4096`.
   The v0.9 training data has p95 seq length = 7,310. Sequences will be truncated at 4096.
   If this hurts reward signal quality, reduce `num_generations` to 2 and try 6144.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| OOM during model load peak (~126 GB) | Medium | Pre-run cleanup; `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`; see `01-docker-build.md` |
| Megatron backend not in container image | Low | `nano-v3` branch includes it; verify at build time |
| NeMo Gym math env reward too sparse | Medium | Start with competition data directly; wrap `validate_metric.py` as custom reward |
| ptxas sm_121a compilation failure | Low | Dockerfile.spark already patches ptxas; see `07-troubleshooting.md` |
| Checkpoint export script missing | Medium | `convert_lora_to_hf.py` is in NeMo RL `nano-v3`; validate it exists before full run |
