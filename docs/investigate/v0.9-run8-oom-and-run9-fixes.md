# v0.9 Run8 OOM Root Cause and Run9 Fixes

Investigation into the GB10 training failures for the v0.9 SFT curriculum, culminating in
run9 training cleanly at ~32 s/step with Unsloth gradient offload and double buffering active.

Logs: `output/train_v9_run8.log`, `output/train_v9_run9.log`

---

## 1. Run8 OOM at step 0 — warmstart + missing GC

### Symptoms

Run8 was launched with a warmstart adapter from the Kaggle v0.9 run7 output
(`warmstart/adapter_config.json`, `peft_version="0.18.1"`). Training OOM'd at step 0:

```
GPU free before training: 48.3GB
  0/1000  [... OOM ...]
```

No steps completed.

### Investigation checklist

- [x] Identify adapter key mismatches between warmstart and DGX LoRA init
- [x] Determine whether warmstart caused trainable-param explosion
- [x] Identify root cause of step-0 OOM (memory, not just warmstart)
- [x] Confirm NemotronH native gradient checkpointing path
- [x] Establish correct fix: warmstart drop vs GC only

### Findings

#### Warmstart adapter key mismatches (92 missing keys)

The Kaggle adapter (`warmstart/`) was saved with `peft_version="0.18.1"` and
`target_modules` that includes `in_proj`/`out_proj`. However, the safetensors files were
missing all 92 keys for the Mamba SSM layers (23 layers × 4 keys: `in_proj.lora_A`,
`in_proj.lora_B`, `out_proj.lora_A`, `out_proj.lora_B`).

PEFT's `PeftModel.from_pretrained` treats missing keys as "newly added" — it initializes
them with fresh random LoRA A/B weights rather than raising an error. This produces:

- **883,873,792 trainable params** (vs run9 fresh init: 27,711,488)
- The count inflation is consistent with loading the full Kaggle routed-expert adapter
  (418 MoE+attention keys) plus newly-initialized Mamba keys

Per the Kaggle notebook comment: "Always start from None when adding new target modules."
Starting from a warmstart with partial key coverage produces an inconsistent adapter state.

#### Warnings observed in run8 logs

| Warning | Source | Root cause |
|---|---|---|
| `UserWarning: Unexpected keyword arguments ['peft_version']` | `peft==0.14.0` loading adapter saved with peft 0.18.1 | Version mismatch; harmless |
| `UserWarning: trust_remote_code=True` | `FastLanguageModel.from_pretrained` | Security noise; removed |
| 92 missing adapter keys | PEFT warmstart | Kaggle adapter missing Mamba keys |
| `padding_free=False` | SFTConfig kwarg | Not valid on DGX Unsloth build |

#### `gradient_checkpointing=False` → step-0 OOM

Run8 used `gradient_checkpointing=False` in `SFTConfig`, matching the prior v0.4 config.
However, on the GB10 at `seq_len=4096` with 128 MoE experts, this is fatal:

- Without GC, every layer's activation tensors are retained in CUDA for the backward pass
- 30B MoE model with 128 experts at seq=4096: estimated 20–40 GB of retained activations
- After loading (48.3 GB free), the first backward allocation exhausts CUDA memory
- Step 0 never completes — OOM before any gradient update

The prior v0.4 investigation (see `docs/investigate/v0.4-oom-training.md`) found the same
root cause at seq=8192 but it took ~37 steps to exhaust reclaimable pages. At seq=4096
with 128 experts, the pool exhausts immediately at step 0.

Setting `gradient_checkpointing=True` in SFTConfig causes SFTTrainer to call
`model.gradient_checkpointing_enable()`, which raises:

```
ValueError: NemotronHForCausalLM does not support gradient checkpointing.
```

This is because `NemotronHForCausalLM.supports_gradient_checkpointing = False`. The
underlying `_set_gradient_checkpointing()` / `GradientCheckpointingLayer` path works
(see `docs/adr/0004-gradient-checkpointing-nemotron.md`). The Kaggle Unsloth build
patches away the ValueError; the DGX build does not.

### Decision: drop warmstart, start fresh

Given:
1. 92 missing Mamba keys → inconsistent adapter state regardless of the OOM fix
2. 883M trainable params (full Kaggle adapter loaded) = wrong starting point
3. v0.9 plan: "Always start from None" for fresh target module coverage

Run9 was launched with `WARMSTART_ADAPTER=None`. Fresh `FastLanguageModel.get_peft_model`
initializes all 9 target modules cleanly: 27,711,488 trainable params (correct).

## 2. Run9 training crashes — two fixes

### Crash 1: `padding_free` kwarg

```
TypeError: SFTConfig.__init__() got an unexpected keyword argument 'padding_free'
```

**Root cause**: The Kaggle Unsloth build script patches `SFTConfig.__init__` to accept
`padding_free` as a pass-through. The DGX Unsloth build (`unsloth==2026.6.2`) does not.
The kwarg came from copying the Kaggle notebook's `SFTConfig(padding_free=False, ...)`.

**Fix**: Removed `padding_free=False` from `SFTConfig` in `train_v9_sft.py`. Unsloth on
DGX auto-enables padding-free when it determines the model supports it:
```
🦥 Unsloth: Padding-free auto-enabled, enabling faster training.
```

### Crash 2: `ValueError` from `gradient_checkpointing_enable()`

```
ValueError: NemotronHForCausalLM does not support gradient checkpointing.
```

**Root cause**: Changing `gradient_checkpointing=False` → `True` in `SFTConfig` (the fix
for the step-0 OOM) causes `Trainer.train()` to call `model.gradient_checkpointing_enable()`
before training starts. This hits the `supports_gradient_checkpointing=False` guard.

The fix from `docs/investigate/v0.4-oom-training.md` already enables native GC via
`_set_gradient_checkpointing()` before SFTConfig is constructed. The remaining problem is
that SFTTrainer then calls `gradient_checkpointing_enable()` again — and that call raises.

**Fix**: After the native GC setup, install a no-op override on the model instance:

```python
model.gradient_checkpointing_enable = lambda **kwargs: None
```

This lets SFTTrainer call `gradient_checkpointing_enable()` without error. The native GC
is already active (confirmed by the "Gradient checkpointing enabled" print before training),
so the no-op does not regress memory behavior.

## 2b. Dockerfile build failure — `26.06-py3` not released

This was a separate issue from the run9 training crashes. While investigating the CUDA
version mismatch (`torch.version.cuda=12.1` vs toolkit 13.2 in the 26.04 container), the
Dockerfile base was updated to `26.06-py3` in anticipation of an upcoming NVIDIA NGC release.

```
ERROR: failed to build: nvcr.io/nvidia/pytorch:26.06-py3: not found
```

**Root cause**: `nvcr.io/nvidia/pytorch:26.06-py3` does not exist (June 2026 release had
not yet been published by NVIDIA to NGC). `docker manifest inspect` confirmed only
`26.05-py3` was available.

**Fix**: Changed `FROM` to `nvcr.io/nvidia/pytorch:26.05-py3`.

This build was not required for run9 (the workspace bind-mount makes script changes live
without an image rebuild). The 26.05 image rebuild is deferred until after run9 completes.

## 3. Changes to `train_v9_sft.py`

| Change | Location | Reason |
|---|---|---|
| Removed `trust_remote_code=True` | `FastLanguageModel.from_pretrained` | Noise; not needed with transformers 5.5.3 native NemotronH |
| Changed `gradient_checkpointing=False` → `True` | `SFTConfig` | False silently disables native GC → step-0 OOM |
| Removed `padding_free=False` | `SFTConfig` | Not a valid kwarg on DGX Unsloth build |
| Added `model.gradient_checkpointing_enable = lambda **kwargs: None` | After native GC setup | Prevents SFTTrainer from re-raising ValueError |
| Added GRPO noise filter around `import unsloth` | Top of script | Unsloth prints via `print()`, not `warnings`; suppressed 2 GRPO-only messages |
| Added `--ckpt-every N` arg + `_PeriodicAdapterSave` callback | Bottom of `main()` | Periodic checkpoint to `<output_dir>_ckpt` (overwrites same path, constant disk) |

### `_PeriodicAdapterSave` callback

```python
if args.ckpt_every > 0:
    from transformers import TrainerCallback, TrainerState, TrainerControl
    _ckpt_dir = args.output_dir + "_ckpt"

    class _PeriodicAdapterSave(TrainerCallback):
        def on_step_end(self, ta, state: TrainerState, control: TrainerControl, **kw):
            if state.global_step > 0 and state.global_step % args.ckpt_every == 0:
                model.save_pretrained(_ckpt_dir)
                print(f"[ckpt] step {state.global_step} → {_ckpt_dir}", flush=True)
            return control

    trainer.add_callback(_PeriodicAdapterSave())
```

Default: `--ckpt-every 50`. Overwrites the same `_ckpt` directory each time — constant
disk usage. Allows recovery if run is killed mid-training.
