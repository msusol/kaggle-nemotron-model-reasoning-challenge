## What is GRPO?

**Group Relative Policy Optimization** is the reinforcement learning algorithm DeepSeek used
to train DeepSeek-R1's reasoning ability. The key insight: instead of training on human-written
or externally-generated CoT, you let the model generate its own reasoning and reward it when
it gets the right answer.

### How it works

For each training problem, generate a *group* of N responses (e.g. N=8):

```
Problem: "In Alice's Wonderland, numbers are secretly converted..."
Response 1: <think>step-by-step reasoning A</think>  \boxed{42}  ← correct ✓  reward = 1
Response 2: <think>step-by-step reasoning B</think>  \boxed{41}  ← wrong   ✗  reward = 0
Response 3: <think>step-by-step reasoning C</think>  \boxed{42}  ← correct ✓  reward = 1
...
Response 8: <think>step-by-step reasoning H</think>  \boxed{43}  ← wrong   ✗  reward = 0
```

Score each response. Compute the *relative advantage* within the group — responses that scored
above the group mean get a positive gradient signal; below get negative. Update the model to
increase the probability of correct responses and decrease the probability of wrong ones.

**No human-written reasoning required.** The only verifier needed is: does the extracted
answer match ground truth? This is exactly the verification we already do in `validate_metric.py`.

### Why GRPO over SFT

| | SFT (v0.1–v0.4) | GRPO (v0.5) |
|---|---|---|
| Training signal | Fixed CoT labels | Model's own generations |
| Reasoning diversity | Limited to training data | Emerges from exploration |
| Data requirement | High-quality CoT needed | Only problems + answers needed |
| Self-improvement | One-shot | Iterative — model improves its own reasoning |
| Implementation | `SFTTrainer` | `GRPOTrainer` (TRL 0.15.2) |

GRPO is how DeepSeek-R1 learned to produce the explicit chain-of-thought reasoning that
makes it so effective — and it's directly applicable here because we have 9,500 competition
problems with known ground-truth answers.

## The KV Cache Bug — Why GRPO Is Slow on Nemotron (and Why We're Already Fixed)

[cite:145] GRPO requires token-by-token autoregressive generation (unlike SFT which is a
single parallel forward pass). Without a working KV cache, each new token recomputes all
previous tokens from scratch: **~2 tokens/sec** instead of **~38 tokens/sec** — a 20×
slowdown that makes a 500-step GRPO run take days instead of hours.

**The bug**: `prepare_inputs_for_generation()` passes the KV cache as `past_key_values`
but `forward()` expects it as `cache_params`. Name mismatch → cache silently dropped into
`**kwargs` → no error, no warning, just full recomputation every token.

**The fix**: `transformers >= 5.3.0` corrects the parameter mapping natively.
Two additional requirements:
- Remove `trust_remote_code=True` — even with 5.5.3 installed, that flag pulls the old
  buggy `modeling_nemotron_h.py` from the HF model cache, overriding the library fix
- Keep `gradient_checkpointing=False` — NemotronH doesn't declare support; will raise
  `ValueError` if enabled

**Our current setup already has all three fixes:**

| Fix | Status |
|---|---|
| `transformers==5.5.3` | ✅ `Dockerfile.gb10-26-01` |
| No `trust_remote_code=True` | ✅ Removed in prior session |
| `gradient_checkpointing=False` | ✅ Already in config |

GRPO should run at ~38 tok/sec on the GB10 with no additional changes to the model loading.

### Reward function

```python
import math, re

BOXED_RE = re.compile(r"\\boxed\{([^{}]+)\}")

def reward_fn(completions, ground_truths, **kwargs):
    """Returns list of rewards in [0, 1] — one per completion."""
    rewards = []
    for completion, truth in zip(completions, ground_truths):
        pred = extract_answer(completion)
        rewards.append(1.0 if answers_match(pred, truth) else 0.0)
    return rewards
```

Binary rewards (0 or 1) are the simplest and most robust. Optional extensions:
- Partial credit for correct format but wrong answer (+0.1 for `</think>\n\boxed{}` present)
- Length penalty to discourage runaway CoT

## Training Strategy

### Starting point and sequencing options

v0.5 does not require v0.4's synthetic CoT data — GRPO generates its own reasoning.
However, the v0.4 *adapter* is valuable as an initialisation point.

**Why initialisation matters for GRPO:**
GRPO explores by generating N responses per problem and rewarding correct ones. If the
starting model scores near 0% on `bit_manipulation`, all N responses score 0 → uniform
group reward → no gradient signal → the model is stuck on that type early in training.

| Starting adapter | bit_manipulation at step 0 | GRPO gradient signal |
|---|---|---|
| v0.3 | ~4.7% coverage | Sparse — risk of early stall on hard types |
| v0.4a/b | ~16%+ coverage | Richer signal across all 6 types |

**Preferred: init from v0.4 (huikang SFT) adapter.**

The v0.4 adapter is trained on exhaustive algorithmic reasoning traces for all 15,979
problems (including the test set). GRPO starting from this adapter already knows HOW to
do systematic hypothesis testing — it just needs reinforcement for correct answers.
This combination is the clearest path beyond 0.85.

**Sequencing options if time is tight:**
- **Option 1 (preferred):** v0.4 SFT → v0.5 GRPO from v0.4 adapter
- **Option 2 (parallel):** Run v0.5 from v0.3 concurrently with v0.4; take best score
- **Option 3 (fast):** Skip v0.4, GRPO from v0.3 — slower convergence on hard types

### Dataset

Use all 9,500 competition problems (prompts only — no responses). GRPO generates its own
responses during training. This is strictly more data than any SFT run.

### Memory budget

Each GRPO step generates N=8 responses before computing gradients. With `max_new_tokens=2048`
and batch_size=1, peak memory ≈ base model + LoRA + 8 × 2048-token KV cache. The 121 GB
GB10 unified memory should handle this; reduce N to 4 if OOM.

### Expected behaviour

- Early training (steps 1–200): reward improves on easy types (`numeral`, `unit_conversion`,
  `gravity`) first — model already has some signal there from v0.4 SFT
- Mid training (steps 200–500): harder types (`bit_manipulation`, `algebra`) improve as
  the model explores correct reasoning patterns through random variation
- Monitor: reward mean per step, reward variance (should stay > 0 — if all 8 responses
  are correct or all wrong, no gradient signal)

## Open Questions

1. **GB10 memory headroom for N=8 generations** — if OOM, reduce to N=4 or N=6.
2. **KL coefficient tuning** — too high → model barely moves; too low → reward hacking.
   Start at 0.04 (DeepSeek-R1 default) and monitor.
3. **Should GRPO replace or follow v0.4 SFT?** — GRPO from scratch is possible but slower
   to converge; starting from the v0.4 adapter is likely faster.
4. **Format reward** — binary correctness may be enough; adding a small format reward
   (`</think>` present, `\boxed{}` present) could prevent format collapse.

## Competition Compliance — Rule 6 (External Data)

v0.5 GRPO uses **only competition data** (the 9,500 problems + ground-truth answers provided
by the competition) and the Nemotron-3-Nano-30B base model (publicly available). No external
datasets are required — the RL reward signal is derived entirely from the competition's own
ground-truth answers.

**No dataset publication required for v0.5.** The starting adapter (from v0.4a or v0.4b)
was already covered by v0.4 compliance steps. If v0.5 is a winning submission, Section 2.8
(Winners Obligations) requires sharing the full training code and methodology — `train_grpo.py`,
`configs/nemotron_grpo.yaml`, and `run_grpo.sh` cover this.

Note: if the v0.4 synthetic CoT data was used to initialise the adapter that v0.5 fine-tunes
from, the v0.4 dataset publication (Kaggle public dataset) should be completed first to
establish clean data lineage end-to-end.
