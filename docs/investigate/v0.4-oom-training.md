# v0.4 Training-Phase OOM Investigation

Investigation into the second `huikang_v4` training run (2026-05-31) that failed with
exit 137 (kernel OOM kill) at step 37/948 of the training loop.

Log: `output/train_huikang_v4_20260531_150206.log`

This is a **different failure** from the loading-phase OOM documented in
`docs/investigate/v0.4-oom-loading.md`. The empty_cache() loading fix succeeded — the
model loaded fully (401/401 shards). The OOM occurred during training.

### Findings

#### Memory state at training start

After model loading with the empty_cache() fix:

```
cuda free=4.1GB  alloc=64.4GB  reserv=65.8GB
linux free=4.0GB  cached=3.4GB  active_file=0.5GB  inactive_file=2.8GB
```

Total CUDA-accessible pool: 130.7 GB. After loading, only 4.1 GB is immediately
available to CUDA. The remaining ~60 GB is managed by the Linux kernel (OS structures,
page tables, driver metadata, reclaimable page cache). The CUDA driver can request
additional pages from the kernel — this is how training ran for 37 steps — but once
the kernel has nothing left to evict, the next large allocation fails and the OOM
killer fires.

#### Step time pattern

| Step range | Time/step | Interpretation |
|---|---|---|
| 1 | 66.69 s | First forward: CUDA kernel JIT compilation + large `cudaMalloc` expansion |
| 2–9 | 43–49 s | Allocator pool warm; stable compute |
| 10 | 60.08 s | Memory pressure spike — kernel evicting pages for CUDA |
| 11–30 | 42–51 s | Equilibrium; kernel still has page cache to evict |
| 37 | OOM kill | Kernel page cache depleted; no memory to satisfy next allocation |

The slow step 10 (60 s vs 43 s baseline) is the first visible memory-pressure signal:
the CUDA driver requested more physical pages from the kernel for the growing allocator
pool, and the kernel had to evict page cache (I/O latency). From step 11 onward,
enough page cache was evicted to provide headroom for several more steps. By step 37,
the reclaimable pool was exhausted.

#### Why activation memory is so large

`gradient_checkpointing=False` in `SFTConfig` was the prior setting. Without gradient
checkpointing, every layer's activation tensor must be retained in CUDA memory for the
backward pass. For a LoRA-finetuned model, the base model is frozen but all of its
activation tensors must still be stored — they are needed to compute gradients through
the LoRA adapter layers inserted at each target module.

Approximate activation memory at seq_len=8192 for Nemotron-3-Nano-30B-A3B:
- ~62 blocks × hidden activations at seq_len=8192 × hidden_dim
- Plus Q/K/V and attention-weight tensors for attention blocks
- Plus intermediate MLP/Mamba state tensors
- Total: estimated **20–40 GB** of activations stored simultaneously

After loading (64.4 GB model) with only 4.1 GB CUDA free and ~6 GB of reclaimable page
cache: `64.4 + 20–40 (activations) >> 70 GB` available → OOM inevitable.

#### Why `gradient_checkpointing=False` was previously correct — but only for 5 steps

The prior code comment said:

```
# NemotronHForCausalLM does not implement gradient_checkpointing_enable();
# SFTTrainer raises ValueError if gradient_checkpointing=True.
# Empirically, seq_len=8192 + frozen base + LoRA fits the 130 GB unified
# pool without GC (confirmed: run 235341 trained 5 steps at ~33 s/step).
```

Run 235341 confirmed 5 steps. Step 10 in this run (60s) already shows pressure. Five
steps was not long enough to exhaust the kernel's reclaimable pages. It would have
OOM'd somewhere between step 20 and 50.

#### NemotronH has native gradient checkpointing — blocked only by a class flag

Inspection of `transformers.models.nemotron_h.modeling_nemotron_h` in transformers
5.5.3 revealed:

1. **`GradientCheckpointingLayer`** — a custom base class that implements GC in
   `__call__`. When `self.gradient_checkpointing=True` and `self.training=True`, it
   calls `self._gradient_checkpointing_func(partial(super().__call__, **kwargs), *args)`
   instead of the normal forward. This recomputes the block's forward during backward
   rather than storing all activations.

2. **`NemotronHBlock`** inherits from `GradientCheckpointingLayer`:
   ```
   NemotronHBlock.__mro__: [NemotronHBlock, GradientCheckpointingLayer, Module, object]
   ```

3. **`NemotronHModel._set_gradient_checkpointing()`** is fully implemented — it walks
   all modules with a `gradient_checkpointing` attribute and sets the flag and function:
   ```python
   for module in self.modules():
       if hasattr(module, "gradient_checkpointing"):
           module._gradient_checkpointing_func = gradient_checkpointing_func
           module.gradient_checkpointing = enable
   ```

4. **The only blocker**: `NemotronHForCausalLM.gradient_checkpointing_enable()` checks
   `self.supports_gradient_checkpointing` first and raises `ValueError` because the
   class attribute is `False`. `_set_gradient_checkpointing()` has no such guard.

The ValueError from `gradient_checkpointing=True` in SFTConfig comes from SFTTrainer
calling `model.gradient_checkpointing_enable()` which hits this guard. The underlying
mechanism works fine.

### Actions Taken

Enabled gradient checkpointing directly via `_set_gradient_checkpointing()`, bypassing
the `supports_gradient_checkpointing=False` guard:

```python
_gc_func = functools.partial(torch.utils.checkpoint.checkpoint, use_reentrant=False)
try:
    model.base_model.model._set_gradient_checkpointing(
        enable=True, gradient_checkpointing_func=_gc_func
    )
    model.enable_input_require_grads()
    print("Gradient checkpointing enabled (NemotronH GradientCheckpointingLayer, use_reentrant=False)")
except Exception as _e:
    print(f"Warning: gradient checkpointing unavailable: {_e}")
```

`model.base_model.model` is the `NemotronHForCausalLM` inside the PEFT wrapper.
`model.enable_input_require_grads()` is required for PEFT + gradient checkpointing
to propagate gradients through frozen base-model layers to the LoRA adapters.

`SFTConfig.gradient_checkpointing=False` is kept to prevent SFTTrainer from calling
`gradient_checkpointing_enable()` and hitting the ValueError again.

Expected effect: activation memory drops from ~20–40 GB to ~1–5 GB (only block inputs
at each checkpoint boundary are retained; intermediate activations are recomputed during
backward). Step time will increase ~1.5–2× (recompute cost).

See `docs/adr/0004-gradient-checkpointing-nemotron.md` for the decision record.
