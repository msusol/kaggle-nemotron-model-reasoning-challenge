# v0.4 NeMo Framework Plan

## Goal

Train Nemotron-3-Nano-30B with the NVIDIA NeMo framework as an alternative to our TRL
SFTTrainer pipeline, using the same huikang corpus (15,159 train / 820 valid examples).
The NeMo path offers selective activation checkpointing, pre-tokenized dataset loading,
and tighter integration with NVIDIA's training stack.

## Context

- **Status**: Documented and ready to execute — dataset published on Kaggle, configs
  written, Docker command specified. Not yet run; TRL SFTTrainer was used for all v0.4
  runs to date.
- **Why NeMo**: NeMo's `activations_checkpoint_granularity: selective` avoids the
  custom `_set_gradient_checkpointing()` hack required by TRL (NemotronH raises
  `ValueError` on standard HF gradient checkpointing).
- **Dataset**: Pre-tokenized NeMo SFT JSONL published at
  `gdataranger/huikang-nemotron-nemo-sft-r32` on Kaggle (15,159 train / 820 valid).
  Regenerate locally via `scripts/run_convert_jsonl_to_nemo.sh` if needed.
- **Full workspace docs**: `docs/plans/nemotron_dgx_workspace/` (steps 1–5 + issues).

## Key config

| Parameter | Value | Notes |
|---|---|---|
| Framework | NeMo 25.02+ | Earlier releases broken for NemotronH |
| LoRA r | 32 | Competition maximum |
| lora_alpha | 32 | Matches TRL runs |
| target_modules | q/k/v/o_proj, in/out_proj, up/down_proj | Same as TRL; excludes lm_head, conv1d, gate |
| seq_length | 8192 | Matches v0.4 TRL runs |
| micro_batch_size | 1 | Required at seq=8192 with 128 GB memory |
| global_batch_size | 4 | Effective gradient accumulation |
| GC method | selective, uniform | NeMo native — avoids HF GC ValueError |
| System prompt | `"Solve the problem step by step. Put your final answer in \boxed{}."` | Baked into pre-tokenized dataset |

**Note on system prompt**: the NeMo dataset was tokenized with the system prompt injected
(same as our TRL v0.4-r2 approach). This means NeMo training inherits the same
system-prompt-vs-augmenter-category contradiction identified in the regression analysis
(`docs/investigate/v0.4-kaggle-regression.md §3`). A NeMo re-run would need the same
Fix 4 Option A (empty system) applied at re-tokenization time.

## Known issues

See `docs/plans/nemotron_dgx_workspace/05_NEMOTRON_FRAMEWORK_ISSUES.md` for the full
list. Key constraints:

- **4-bit / 8-bit quantization**: broken — MoE expert tensors cause BitsAndBytes shape
  mismatches. BF16 only.
- **`trust_remote_code=True`**: avoid — overrides the native KV-cache fix in
  `transformers>=5.5.3`.
- **`target_modules="all-linear"`**: avoid — wraps all 128 expert copies individually,
  producing billions of LoRA params and OOM. Use explicit module list.
- **HF `gradient_checkpointing_enable()`**: not supported — NemotronH raises ValueError.
  Use NeMo's selective GC or the TRL `_set_gradient_checkpointing()` workaround.

## Post-training: convert to HF PEFT format

```bash
python /opt/NeMo/scripts/checkpoint_converters/convert_nemo_to_hf_lora.py \
    --input_nemo_file /data/nemotron_runs/.../checkpoints/last.nemo \
    --output_hf_directory /data/nemotron_hf_lora/
```

Then evaluate and submit using the standard `scripts/infer_lora.py` +
`scripts/package_submission.sh` pipeline.

## Decision gate

NeMo training is a parallel option to TRL, not a replacement. Run it if:
- v0.5 GRPO from v26 does not reach 0.85+, and we want a cleaner SFT baseline
- We want to test whether NeMo's selective GC gives better throughput than our TRL GC hack

For now, v0.5 GRPO from `output/adapter_huikang_v26` is the priority path.
