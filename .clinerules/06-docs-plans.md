# Planning Document Rules

This document establishes guidelines for implementation plans in `docs/plans/`.

## Key Principles

**Minimal by default:** New plans should start simple with Goal, Context, and Tasks sections, using checkbox format (`- [ ]`) for synchronization with TODO.md.

**Expand thoughtfully:** Only add sections like Scope, Risks, or Decision Log when the work spans multiple systems, extends across sessions, or involves meaningful dependencies.

**Clear separation:** Plans focus on "how and when" execution details, while specs handle architectural "what and why" rationale.

## Core Guidelines

- Keep tasks concise and action-oriented for easy copying into tracking systems
- Avoid forcing elaborate templates onto straightforward work
- Add sections incrementally rather than creating empty placeholders
- Preserve readability by evolving existing files instead of duplicating them

## When to Expand

Introduce additional structure when:
- Work touches multiple components or systems
- Implementation will span several sessions
- Task lists become unclear or unwieldy
- Risks, dependencies, or rollout concerns exist
- Handoff to another person may occur
- Unknown factors surface during execution

## Relationship to Other Docs

The guidance distinguishes three document types: specs for design rationale, plans for sequencing tasks, and investigation files for debugging work.
