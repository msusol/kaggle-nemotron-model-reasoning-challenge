## Why v0.4a/b Was Superseded

The original v0.4 plan (Nemotron self-gen or DeepSeek-R1 via vLLM) was designed to fill type
coverage gaps. That became unnecessary once we found the publicly available `samvalladares/huikang-nemotron-artifacts` corpus, which:

- Covers **15,979 unique problems** — the full training set (6,355) plus the **test set (9,624)**
- Contains exhaustive algorithmic reasoning traces (~3,292 median, ~6,676 p90 tokens)
- Achieves **0.85 Kaggle score** in the reference notebook when used directly
- Is already downloaded at `.cache/huikang-artifacts/huikang-nemotron-artifacts.zip`

See [`docs/investigate/huikang-pipeline.md`](../investigate/huikang-pipeline.md) for the full
investigation into how the corpus was generated and why it achieves 0.85.

## What Makes the Corpus Different

The CoT traces are not "think and guess" — they are complete hypothesis-testing programs.
For `bit_manipulation`, the model tries every combination of 2-bit operations (AND, OR, XOR,
NOT, OR-NOT, XOR-NOT, AND-NOT…) against all 8 examples to find the exact rule, then applies
it to the query. Starting loss at step 1 was 0.386 (vs our v0.3 starting at 22.9) — the
data is perfectly aligned to the model's pre-training distribution.

## Data Pipeline

### 1. Extract and decode corpus

The corpus is pre-tokenized with Nemotron token IDs. Decode back to text using the
Nemotron tokenizer and convert to our standard JSONL format.

```bash
python scripts/extract_huikang_corpus.py \
    --zip .cache/huikang-artifacts/huikang-nemotron-artifacts.zip \
    --out-train data/v0.4_train.jsonl \
    --out-valid data/v0.4_valid.jsonl \
    --valid-split 0.05
```

Script reads each `corpus/corpus/{id}/synthetic.jsonl`, decodes tokens, reconstructs
`{id, prompt, response, system}` JSONL records. Splits 95/5 train/valid.

Expected: ~15,180 train + ~799 valid examples.

### 2. Verify type distribution

```bash
python3 -c "
import json
from collections import Counter
with open('data/v0.4_train.jsonl') as f:
    rows = [json.loads(l) for l in f]
# classify by prompt text
def classify(p):
    p = p.lower()
    if 'bit manipulation' in p: return 'bit_manipulation'
    if 'gravitational' in p: return 'gravity'
    if 'unit conversion' in p: return 'unit_conversion'
    if 'encryption' in p: return 'cipher'
    if 'numeral system' in p: return 'numeral'
    if 'transformation rules' in p: return 'algebra'
    return 'other'
c = Counter(classify(r['prompt']) for r in rows)
for t, n in sorted(c.items(), key=lambda x: -x[1]):
    print(f'{t:<20} {n:>6} ({100*n/len(rows):.1f}%)')
"
```

Updated in `configs/nemotron.yaml` and `scripts/train_lora.py`.

## Memory Budget on GB10

The 0.85 notebook peaked at 87.5 GB on 96 GB (RTX Pro 6000) at `micro_batch_size=4,
MAX_SEQ_LEN=8192` with Unsloth. We have 121 GB — 33.5 GB headroom without Unsloth.
Starting with `batch_size=1, grad_accum=16`. Increase `batch_size` to 4 if memory allows.

## Open Questions

1. **LR tuning** — 1e-5 is safe; if v0.4 underperforms 0.85, try 5e-5 or 2e-4 (the 0.85
   notebook uses 2e-4 but with a custom AdamW + linear decay, not cosine).
2. **Mamba fast path** — the 0.85 notebook forces `is_fast_path_available=True`. Our
   transformers 5.5.3 native implementation may not enable this during training. Worth
   patching in `train_lora.py` if loss convergence is slower than expected.
3. **lm_head LoRA** — standard PEFT should handle it; the 0.85 notebook had to manually
   re-add it only because Unsloth strips it for MoE models.
